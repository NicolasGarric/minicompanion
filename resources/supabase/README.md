# Supabase SQL pack

Every SQL file to paste into **Supabase → SQL Editor → New query → Run**, in plain ASCII so it
copies cleanly. Generated by `scripts/build-sql-resources.sh` from `supabase/` (the source of truth):
run it again after adding a migration, never edit these copies by hand.

| Demo data | removed from the live database (checked 2026-10-28) |

## What to run

1. `0_check_status.sql`: read-only. Lists every migration as `applied` or `TO APPLY`.
2. Then one of these:
   - `2_apply_latest_migration.sql`: only the latest migration (21). Use `1_apply_all_migrations.sql` if 20 is not applied yet: it applies 20 and 21 and skips the rest.
   - `1_apply_all_migrations.sql`: all migrations in one script. Migrations already in the
     database are skipped automatically, so it is safe to run on any database, new or old
     (migration 03 is a policy fix that simply runs again).
3. Run `0_check_status.sql` again: every line should say `applied`.
4. `3_security_check.sql`: security check of the live database. It changes nothing (it always ends
   with an error whose message is the report). Every line should start with `OK`.

The `migrations/` folder holds the same migrations one file per step (`01_core.sql` … `21_narrative_campaigns.sql`),
for reading or for running one by one, in number order. Unlike the scripts above, these files do not skip
themselves: running one twice stops with "already exists".

## Demo data (`demo/`)

Only for a demo or test project. Fictional stores, players, tournaments; every demo account uses the
password `demo-password-2026`.

| File | What it does |
|---|---|
| `1-seed.sql` … `5-seed_tournament.sql` | Demo data, run in number order after the migrations |
| `fix_demo_friday_table3.sql` | Fixes the demo match shown as 14 – 14 but counted as a win (older seed). Changes 0 or 1 row, safe to run twice |
| `cleanup_demo_data.sql` | Removes **all** demo data and keeps real users' data. Run its PREVIEW part first and read the counts. Afterwards `scripts/check-supabase.mjs` no longer works |

## Notes

- Nothing in this folder contains a password or a secret key. The database password stays in your
  password manager. It leaked once: the owner decided on 2026-10-27 to change it.
- Tested 2026-10-27 on a fresh local Postgres 16 (PostGIS emulated): apply all, re-run (everything
  skipped), apply the latest migration alone on a database at 15, demo fix (1 row then 0), and the 257 RLS
  checks in `supabase/tests/` (287 with migrations 17 and 18).
- To copy the full setup straight to the Windows clipboard instead: `scripts/copy-setup-sql.sh`
  (`--no-seed`, `--from 17`, `--status`, `--print`).
